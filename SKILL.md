# Стандарты C# Desktop (WPF / Avalonia)

Свод обязательных правил написания, ревью и рефакторинга кода. Позиция — ведущий разработчик: правила многозначны там, где практика проверена опытом, и явно помечены как рекомендация там, где допустимы варианты.

## Как применять

- Правила обязательны при генерации нового кода и при ревью. При рефакторинге существующего кода — применять к изменяемой области, не переписывать весь файл молча.
- Если существующий проект следует другим договорённостям (например, `m_`-префиксы или Prism вместо CommunityToolkit.Mvvm) — следовать стилю проекта и явно предупредить пользователя о расхождении с этими правилами.
- Рекомендации помечены словом «рекомендуется»; всё остальное — требования.

## Десять главных правил

1. **MVVM без исключений.** View не содержит бизнес-логики, ViewModel не знает о View (никаких `Window`, `MessageBox`, ссылок на контролы). Подробности — [references/mvvm.md](references/mvvm.md).
2. **CommunityToolkit.Mvvm** вместо ручного INotifyPropertyChanged: `[ObservableProperty]`, `[RelayCommand]`. Исключение — проект уже на Prism/ReactiveUI, тогда его стек.
3. **Async до конца.** Запрещены `.Result`, `.Wait()`, `GetAwaiter().GetResult()`, `async void` вне обработчиков событий. Не делать fire-and-forget без наблюдения Task.
4. **Nullable reference types включены** (`<Nullable>enable</Nullable>`). Предупреждения nullable не подавлять без причины, `!` (null-forgiving) — только с комментарием, почему null невозможен.
5. **DI-контейнер** (Microsoft.Extensions.DependencyInjection). Сервисы — через интерфейсы, регистрация в одном месте (composition root). ServiceLocator-антипаттерн запрещён.
6. **Один тип — один файл**, имя файла = имя типа. Record-структуры DTO допустимо группировать в один файл, если они одной предметной группы.
7. **Конструктор не работает.** В конструкторе — только присвоение зависимостей и инициализация полей. Тяжёлая работа, I/O, загрузка данных — в `InitializeAsync`.
8. **Ничего не дублируется в XAML.** Цвета, кисти, стили, конвертеры — в ResourceDictionary, а не копипастой по разметке. Подробности — [references/xaml.md](references/xaml.md).
9. **Ошибки обрабатываются на границах.** Пустой `catch` запрещён. Все исключения из команд — через общий SafeExecute с логированием и уведомлением пользователя (см. [references/mvvm.md](references/mvvm.md)).
10. **Коллекции в VM — `ObservableCollection<T>`**, изменяются только из UI-потока. Массовые обновления — пачками, без тысяч `CollectionChanged`.

## Структура решения

Минимум 3 проекта (для маленькой утилиты допустим монолит с папками в том же виде):

```
src/
├── App.sln
├── App/                  # composition root: Program/App, App.xaml(axaml), регистрация DI, стили
├── App.Core/             # модели домена, интерфейсы сервисов, DTO; без зависимостей от UI
├── App.Services/         # реализации сервисов: файлы, сеть, БД, платформенные API
├── App.ViewModels/       # ViewModel'и; зависят только от App.Core
└── App.Views/            # для Avalonia; в WPF допустимо слить с App (папки Views/, Controls/)
```

Правила зависимостей: стрелки только внутрь. `App.Core` не знает ни о WPF, ни об Avalonia. ViewModels не ссылаются на Views. Если в Core понадобился `System.Windows` или `Avalonia.*` — архитектурная ошибка.

## Именование

| Сущность | Соглашение | Пример |
|---|---|---|
| Классы, методы, свойства, события | PascalCase | `OrderService`, `LoadAsync` |
| Интерфейсы | I + PascalCase | `IFilePicker` |
| Приватные поля | _camelCase, без `m_`, `s_`, без `this.` | `_logger` |
| Параметры, локальные переменные | camelCase | `cancellationToken` |
| ViewModel | суффикс ViewModel | `MainWindowViewModel` |
| Окна / представления | Window / View / Page | `SettingsWindow`, `UserListView` |
| Сервисы | суффикс Service | `KeyboardHookService` |
| Async-методы | суффикс Async | `SaveDocumentAsync` |
| Dependency/StyledProperty | поле-свойство пара | `FooProperty` / `Foo` |
| Тестовые методы | `Метод_Сценарий_Ожидание` | `SaveAsync_NoFile_Throws` |

`x:Name` в XAML — только когда элемент реально адресуется из кода или биндинга; именование PascalCase. Не раздавать имена всем элементам подряд.

## Стиль C#

Целевой рантайм — современный .NET (8+), C# 12+. Если проект на .NET Framework 4.8 — современные фичи не предлагать, пометить это в ответе.

- `file-scoped namespace` всегда; `global using` для системных пространств в отдельном файле или csproj (`<Using Include=.../>`).
- `var` — когда тип очевиден из правой части (`var client = new HttpClient()`); явный тип — для фабричных методов и неочевидных возвратов.
- Использовать современный язык: pattern matching, switch-выражения, `record` для DTO и сообщений, `init`-свойства, коллекции `[]`, `required` вместо длинных конструкторов DTO, `ArgumentNullException.ThrowIfNull`.
- Скобки `{}` всегда, даже для однострочного `if`.
- `#region` не использовать: нужность региона — симптом, что класс надо делить. Допустимо только вокруг сгенерированного кода.
- Ориентиры объёма: метод ≤ ~40 строк, класс ≤ ~400 строк. Не догма, но превышение — повод обосновать или разделить.
- Магические числа и строки → именованные константы. Строки, видимые пользователю, — в ресурсы локализации, не в коде и не в XAML хардкодом.
- Возвращать наиболее абстрактный подходящий тип (`IReadOnlyList<T>` из публичных API), принимать наиболее общий (`IEnumerable<T>`, `Stream`).
- Метод расширения — только если он читается как часть типа; не засорять `object` и `string` без нужды.
- Комментарии — отвечают «почему», а не «что». XML-doc — для публичного API библиотек; в приложении — по необходимости.

## Асинхронность и потоки

Ключевые правила; потоковая специфика фреймворков — в [references/wpf.md](references/wpf.md) и [references/avalonia.md](references/avalonia.md).

- `async Task` / `async Task<T>` — единственные допустимые async-сигнатуры кроме обработчиков событий (`async void` только там).
- `ConfigureAwait(false)` — в библиотечном коде без зависимости от UI; в VM и приложении не использовать (возврат в UI-контекст нужен).
- Фоновая работа — `Task.Run` с `CancellationToken`; долгие операции — с `IProgress<T>`.
- `CancellationToken` — последний параметр async-методов, пробрасывать вниз, не игнорировать.
- Одиночный fire-and-forget — только через явный SafeFireAndForget с наблюдением исключений.

## Ошибки и логирование

- Логирование — `ILogger<T>` (Microsoft.Extensions.Logging), структурированные сообщения-шаблоны, не интерполяция.
- Исключения — конкретных типов; не ловить `Exception` без перевыброса или логирования; не использовать исключения для обычного потока управления.
- Граница приложения (UI-команды, события жизненного цикла) — единая точка перехвата: лог + понятное сообщение пользователю, без stack trace в UI.

## Чек-лист код-ревью

При ревью проверять в этом порядке и выдавать замечания списком «файл:строка — правило — как исправить»:

1. View не тянет логику, VM не тянет UI-типы.
2. INPC/команды через генераторы, нет ручного `PropertyChanged?.Invoke`.
3. Нет блокировок async (`.Result`, `.Wait`), нет безнадзорного fire-and-forget.
4. Все подписки на события имеют отписку или weak-механизм.
5. Коллекции меняются из UI-потока; длинные списки виртуализованы.
6. Строки UI не захардкожены; стили не дублируются.
7. Ошибки не проглатываются; логирование структурированное.
8. Именование и структура файлов по таблице выше.
9. Nullable-аннотации корректны, нет беспричинного `!`.
10. Новый публичный API сервисов — через интерфейс и зарегистрирован в DI.
