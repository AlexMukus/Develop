# Производительность и память (WPF / Avalonia)

Правила предотвращения типичных проблем desktop-UI: фризы, утечки, раздутое потребление памяти.

## Содержание

- Принцип: сначала измерять
- UI-поток
- Коллекции и виртуализация
- Память и утечки
- Изображения
- Запуск приложения
- INPC и привязки

## Принцип: сначала измерять

- Оптимизация без профилировщика запрещена. Инструменты: PerfView, dotMemory/dotTrace, Visual Studio Diagnostics, встроенные ETW-события WPF.
- Утверждение «так быстрее» в коде/ревью подкрепляется замером или ссылкой на профилирование.

## UI-поток

- UI-поток делает только UI. Всё дольше ~50 мс (I/O, парсинг, сеть, тяжёлые вычисления) — `Task.Run` + `CancellationToken`, прогресс — через `IProgress<T>`.
- Не «прогревать» UI синхронными ожиданиями: `.Result`, `.Wait()`, `Thread.Sleep` в UI-потоке — фриз интерфейса.
- Частые события (мышь, скролл, сырые данные с устройств) — throttling/debouncing на входе, а не обработка каждого тика.

## Коллекции и виртуализация

- Списки >100 элементов — только с виртуализацией (в WPF включена по умолчанию, что её ломает — см. wpf.md; в Avalonia — `VirtualizingStackPanel`/проверка шаблона панели).
- Не биндить десятки тысяч элементов «на всякий случай»: пагинация, виртуальный скролл, фильтрация до отображения.
- Массовое наполнение `ObservableCollection` — пачкой: расширение `AddRange` с одним уведомлением или пересоздание коллекции. Цикл `Add` из 10 000 итераций в UI-потоке — фриз.
- `CollectionView` (WPF): фильтрация/сортировка на представлении, а не пересозданием коллекции.

## Память и утечки

Проверяемые при ревью источники утечек:

1. **Статические и долгоживущие события.** Подписка короткоживущего объекта на событие статического/долгоживущего — утечка. Лекарство: отписка в Dispose/`Closed`, `WeakEventManager` (WPF), `WeakReferenceMessenger` вместо ручных событий между VM.
2. **`DispatcherTimer` без `Stop`** — тикает вечно, держит цель.
3. **Замыкания в обработчиках**, захватывающие VM/окно, — объект живёт, пока жив обработчик.
4. **`CompositionTarget.Rendering`** (WPF) без отписки — кадровый вызов навсегда.
5. **Binding к свойству объекта без INPC** (WPF): PropertyDescriptor-утечка — объект не собирается, пока жив binding. Правило: всё, что биндится, реализует INPC или иммутабельно.
6. **Кэши без границ** (картинки, VM, DTO) — политика вытеснения или weak-ссылки.

- Реализация `IDisposable` там, где объект владеет неуправляемыми ресурсами, таймерами, подписками; VM со сложным временем жизни — `IDisposable` и вызов из навигатора/окна.
- `GC.Collect()` в продуктовом коде запрещён — это маскировка проблемы.

## Изображения

- Картинки для списков/превью — декодировать в целевой размер (`DecodePixelWidth`/`DecodePixelHeight` в WPF, `DecodeToWidth` в Avalonia), а не грузить 12 Мп в плитку 64×64.
- WPF: созданные в коде `BitmapImage`/кисти — `Freeze()` после настройки.
- Потоки с файлами изображений закрывать сразу (`CacheOption.OnLoad` + `using`), иначе файл залочен.
- Иконки — векторные (Path/StreamGeometry) там, где возможно.

## Запуск приложения

- Конструктор `MainWindow` и `App.OnStartup` — лёгкие: показать окно быстро, данные — догружать асинхронно с индикатором.
- Сервисы в DI — ленивые по умолчанию; не поднимать всю вселенную в composition root. Синглтон с тяжёлым конструктором — отложенная инициализация.
- ReadyToRun/trim/AOT — обсуждать отдельно; не включать публикационные оптимизации «для галочки» без замера холодного старта.

## INPC и привязки

- Не стрелять `PropertyChanged` без изменения значения (генератор `[ObservableProperty]` сам проверяет равенство — ручной код должен делать так же).
- Зависимые свойства — через `[NotifyPropertyChangedFor]`, а не ручным спамом `OnPropertyChanged(nameof(...))` из десяти мест.
- `PropertyChanged` с `null`/`string.Empty` («обновилось всё») — только при реальной массовой смене состояния; как привычка — запрещено.
- Тяжёлые `get`-свойства, участвующие в привязках (файл, сеть, большой LINQ), — пересчитывать явно и кэшировать, не в геттере.
