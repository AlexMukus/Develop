# Конституция KeyboardTester

## Основные принципы

### I. Строгая многоуровневая архитектура
Зависимости текут только в одном направлении: Core не имеет ссылок на проекты и не использует
Windows API; Infrastructure и Application ссылаются только на Core; UI
собирает всё воедино и зависит от Application и Infrastructure. Обратные
ссылки запрещены и должны отклоняться на ревью. Обоснование: доменная
логика (анализ chatter, статистика, ghosting) остаётся переносимой и покрываемой юнит-тестами;
специфика Windows (Raw Input, P/Invoke) остаётся за границей уровня.

### II. Контроль качества «Ноль предупреждений»
Решение собирается с `TreatWarningsAsErrors=true` и не должно выдавать предупреждений
ни в одной конфигурации. Nullable reference types включены везде; код использует
пространства имён с областью видимости файла, явные модификаторы доступности и обязательные фигурные скобки.
Публичные типы и члены снабжаются XML-документацией на русском языке. Обоснование: предупреждения
в приложении, ориентированном на измерения, маскируют реальные дефекты (размеры структур, сигнатуры interop);
чистая сборка — самый дешёвый детектор регрессий.

### III. Соглашения MVVM и WPF
ViewModels находятся в слое Application и используют генераторы исходного кода CommunityToolkit.Mvvm
(`[ObservableProperty]`, `[RelayCommand]`); представления остаются без логики.
Все сервисы регистрируются как singleton в графе DI, который разрешается в
`App.OnStartup` до показа главного окна, поскольку `RawInputCapture` и
`StatisticsEngine` требуют привязки к UI-потоку. Стили, общие для всех тем, находятся
в `Resources/Styles.xaml` на `DynamicResource` и должны переживать переключение тем.
Обоснование: единая точка композиции и генераторные VM делают граф MVVM
предсказуемым и предотвращают баги диспетчера и поиска ресурсов.

### IV. Дисциплина тестирования
Тесты используют xUnit с FluentAssertions и Moq, именуются `Method_Scenario_ExpectedResult`
(в проектном соглашении на русском: `Метод_Сценарий_ОжидаемыйРезультат`). Чистая логика
(анализ chatter, статистика, layouts) покрывается юнит-тестами; Raw Input,
сессии, ViewModels и UI-конвертеры — интеграционными тестами через фейки
(`FakeNativeMethods`, `FakeRawInputCapture`) и STA-хелпер. WPF-компоненты
запускаются в STA-потоке. `dotnet test KeyboardTester.sln`
должен быть полностью зелёным, прежде чем задача считается завершённой. Обоснование: ценность
приложения — корректность измерений, которая доказуема только через тесты; фейки
удерживают зависимости от Windows-оборудования вне пути тестирования.

### V. Тестируемость и работа только локально
Все взаимодействия с Win32 изолированы за интерфейсами (`INativeMethods`), чтобы их можно было
подменять в тестах; объявления P/Invoke должны точно соответствовать документации Win32
по сигнатурам и размерам структур. Приложение не выполняет сетевых вызовов
и хранит настройки, историю сессий и логи только в
`%AppData%/KeyboardTester/`. Новая работа следует YAGNI: нет спекулятивных фич,
зависимостей или абстракций. Обоснование: автономный диагностический инструмент
должен быть надёжным и самодостаточным; точные контракты interop и возможность фейкинга —
то, что делает сбои диагностируемыми.

## Технологический стек и ограничения

- Язык/рантайм: C# 12 на .NET 9; UI — WPF (только Windows, `net9.0-windows`).
- Версии зависимостей централизованы в `Directory.Packages.props` (CPM);
  записи `PackageReference` никогда не содержат встроенных версий.
- `SkiaSharp.Views.WPF` зафиксирован на 2.88.9 (3.x тянет ассеты только для .NETFramework,
  NU1701); не обновлять без явной проверки.
- Логирование через Serilog в `%AppData%/KeyboardTester/logs/`; сообщения UI и лога
  на русском языке; ресурсы локализации находятся в `Strings.Designer.cs`.
- Экспорт в PDF/отчёты — вне скоупа; QuestPDF не используется и не должен добавляться.
- Стандарты кодирования: `.editorconfig`, `Directory.Build.props`, `AGENTS.md` и
  скилл `csharp-desktop-rules` (`.roo/skills/csharp-desktop-rules/`) являются
  обязательными источниками; проектные соглашения имеют приоритет над общими правилами скилла при конфликте
  (документированные расхождения — намеренные).

## Рабочий процесс разработки и контрольные ворота качества

- Перед написанием или ревью C#/XAML прочитайте точку входа скилла `csharp-desktop-rules`;
  подключайте справочные файлы (`mvvm.md`, `xaml.md`, `wpf.md`,
  `performance.md`) по задаче, а не целиком.
- Контроль качества при каждом изменении: `dotnet build KeyboardTester.sln` без
  предупреждений, затем полностью зелёный `dotnet test KeyboardTester.sln`.
- Портативные релизные сборки проходят через `build-portable.ps1` (запускает тесты, если
  не указан `-SkipTests`) и попадают в `artifacts/`; CI повторяет ту же последовательность ворот.
- Релизы: поднимите `<Version>` в `Directory.Build.props`, запушьте тег `vX.Y.Z`;
  `release.yml` создаёт GitHub Release из портативного ZIP.
- Когда изменение затрагивает что-то, что документирует `AGENTS.md`, обновите `AGENTS.md` в
  том же изменении.

## Управление

Эта конституция имеет приоритет над всеми остальными практиками кодирования в репозитории;
`AGENTS.md` и скилл `csharp-desktop-rules` являются подчинёнными оперативными
руководствами и не должны противоречить ей. Поправки требуют: документированный diff в
отчёте о влиянии синхронизации, поднятие семантической версии (MAJOR при удалении
или переопределении принципов, MINOR при добавлении или существенном расширении принципов/разделов,
PATCH для уточнений и формулировок), а также полностью зелёная сборка и прогон тестов
перед коммитом. Все ревью кода должны проверять соответствие этим принципам;
любое отклонение должно быть обосновано в описании изменения. Обнаруженные расхождения
между скиллом и проектными соглашениями разрешаются в пользу проекта,
отмечаются пользователю и оставляются на месте, а не переписываются молча.
